# Chapter 15: The Keycloak Theme (`apps/keycloak-theme`)

This is the fifth JavaScript workspace, and it's a genuinely different kind of app from the
other four — it isn't a page the browser navigates to as part of using Anamnys directly.
It's a React application compiled into a **Keycloak login theme**, so that the pages
Keycloak itself serves during the OIDC redirect look like the rest of the product instead
of Keycloak's stock UI.

## Why this exists, and what it deliberately doesn't change

Chapter 6 already told you the headline reason: the alternative — letting each SPA own its
own login form and having the BFF exchange credentials directly (Resource Owner Password
Credentials) — was considered and rejected. That grant type is removed outright in OAuth
2.1 and disabled by default in Keycloak 26, and choosing it would mean reimplementing
password reset, email verification, and step-up MFA as application code — precisely the
work self-hosting Keycloak was meant to avoid.

Keycloakify's approach keeps the mechanism completely intact: the browser still gets
redirected to Keycloak, still runs the full Authorization Code + PKCE flow. **Only the page
Keycloak renders during that redirect is ours.** Every server-side mechanism the HIPAA
posture from Chapter 6 depends on — brute-force lockout, required actions, TOTP/WebAuthn
enrollment, password reset, email verification — keeps working exactly as Keycloak
implements it, because none of that logic has moved into this theme at all.

## What's actually customized

`KcPage.tsx` is short enough to make this precise:

```tsx
switch (kcContext.pageId) {
  case 'login.ftl':
    return <Login kcContext={kcContext} i18n={i18n} />;
  case 'login-otp.ftl':
    return <LoginOtp kcContext={kcContext} i18n={i18n} />;
  case 'login-reset-password.ftl':
    return <LoginResetPassword kcContext={kcContext} i18n={i18n} />;
  default:
    return <DefaultPage kcContext={kcContext} i18n={i18n} classes={classes}
      Template={DefaultTemplate} doUseDefaultCss={true}
      UserProfileFormFields={UserProfileFormFields}
      doMakeUserConfirmPassword={doMakeUserConfirmPassword} />;
}
```

Only three pages get the custom Anamnys-branded `Template` and React components: the login
form itself, the OTP challenge, and the password reset flow. Everything else Keycloak might
ever render — registration, email verification, error pages, account update flows, and so
on — falls through to `DefaultPage`, Keycloakify's own default theme and template
unmodified. This matches the design spec's stated scope exactly, and it's a good example
of a deliberately narrow customization: only the pages a typical login actually touches are
worth the maintenance cost of a custom implementation.

**One theme serves all three realms.** There's no `anamnys-providers` theme, a separate
`anamnys-patients` theme, and so on — a single Keycloakify build produces one theme, and
each realm's JSON simply sets `loginTheme: "anamnys"` and points at it. Any per-realm
branding difference is meant to be handled inside the theme by switching on
`kcContext.realm.name` (a CSS variable or similar), not by tripling the component code for
what would otherwise be a cosmetic difference.

## Structure

`src/login/` holds the pieces: `KcContext.ts` (Keycloakify's typed context describing
whatever page and data Keycloak handed to the theme), `Template.tsx` (the custom Anamnys
shell wrapping the three overridden pages), `branding.ts` and `i18n.ts`, and `pages/`
containing `Login.tsx`, `LoginOtp.tsx`, and `LoginResetPassword.tsx`. `kc.gen.tsx` at the
project root is auto-generated by Keycloakify's own tooling (`update-kc-gen`) — its header
says so explicitly, in the same spirit as the `routeTree.gen.ts` files from Chapter 11 —
and isn't meant to be hand-edited.

This app imports from `@anamnys/shared` too, specifically for `Button`, `TextField`, and
the shared i18n resources — the same reasoning Chapter 12 already covered: the goal is for
these pages to look like the rest of the product without reinventing its component
library from scratch.

## The dependency-version risk — and evidence it worked out

The implementation design document flagged a genuine, specific risk before this app was
built: Keycloakify 11.16.0 declares no `peerDependencies` and was developed against Vite 5,
React 18, and TypeScript 4.9 — while this repository runs Vite 8, React 19, and TypeScript
6.0.3. Nothing in npm would *block* installing it regardless; the open question was whether
Keycloakify's Vite plugin actually functions correctly against Vite 8's plugin API. The
design explicitly called this out as the first task to spike before anything else depended
on it, with a documented fallback: let `apps/keycloak-theme` pin its own, older Vite and
TypeScript versions independently in its own `package.json`, since npm workspaces permit
that and this app's build is already independent of the other three SPAs.

Looking at the app as it exists today, that risk resolved cleanly: `apps/keycloak-theme`'s
`package.json` runs the same versions as everywhere else in the repository —
`keycloakify: ^11.16.0`, `vite: ^8.0.16`, `typescript: ~6.0.3`, `react: ^19.2.1` — no
divergent pin was needed. This is a small but genuinely reassuring signal if you ever need
to touch this app: the toolchain risk that was worth spiking on turned out not to require
the fallback plan.

## The build pipeline

```json
"build-vite": "tsc -b && vite build",
"build-keycloak-theme": "npm run build-vite && keycloakify build",
"build": "npm run build-keycloak-theme"
```

Two distinct steps, chained: an ordinary Vite production build first, then `keycloakify
build`, which packages that output — plus Keycloak-specific templates and metadata — into
a **jar** (not a loose directory of files). That jar is what lands at
`keycloak/theme/keycloak-theme-anamnys.jar`, which is gitignored, and which
`keycloak/Dockerfile` (Chapter 7) copies directly into `/opt/keycloak/providers/` — provider
loading, not the older `/opt/keycloak/themes/` unpacked-directory convention, which is why
no `--spi-theme` startup argument is needed to make Keycloak notice it.

Because that jar is a build output that has to exist *before* the Keycloak image can be
built, and it's gitignored (never committed), remember the ordering rule from Chapter 7: a
missing jar fails the Docker build outright, on purpose, rather than silently producing a
Keycloak that serves its own stock login page with nobody noticing. If you're setting up a
fresh environment and Keycloak fails to build with a complaint about a missing theme jar,
this app's build script — run via the root workspace `npm run build`, like every other
app — is the fix, not a Dockerfile change.

With all four SPAs and the theme app covered, Part 7 shifts from what the code does to how
it's verified, shipped, and kept consistent.
